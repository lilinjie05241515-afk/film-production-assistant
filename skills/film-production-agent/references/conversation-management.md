# 分层会话管理

用于本轮要求或有效持续授权覆盖分层会话方式的单个影视项目。新项目已授权按本机制搭建时直接配置分层，不逐项目再询问开关。读取准确作品 root、project_id、当前真实聊天及 `film_conversations` 状态，再确定自己处于哪一层。工具字段以当前定义和 [2.1.0 接入](../../../docs/integration-2.1.0.md)为准。旧项目仅查看不迁移；接续采用时核对原入口与任务，保存一次适用授权，保留真实标题、历史和执行锁。未采用的旧项目按[工作区兼容流程](workspace-management.md)接续。

分层协作适用于已登记的 planning、script、novel、director、art、assets、review 部门；导演与特效共用导演部门，但专业方法和任务模块仍分开。原灵感选定交编剧流程继续有效，其他明确请求按[职责归属与转交](request-routing.md)接续。没有登记的部门由项目总控协调，不能用新层级冒充新增媒体制作能力或常驻执行器。

## 层级与职责

| 逻辑层级 | 处理内容 | 下级 |
| --- | --- | --- |
| 项目总控 | 项目方向、部门间取舍、必要澄清与派发、准确结果汇总 | 灵感、编剧及其他实际需要的部门总控 |
| 部门总控 | 本部门输入核对、只澄清缺项、确认本轮范围、复用或建立话题、任务派发与验收汇总 | 明确的专题讨论或执行话题 |
| 专题讨论 | 同一灵感或议题的持续发散、分支比较、选定后深入、原话及决定记录 | 讨论结果交回部门总控 |
| 执行话题 | 一个准确任务范围内的正文、改稿、制作、检查点及实际成果 | 完成结果交回所属部门总控 |

以当前真实登记区分项目总控、部门总控和执行话题；旧初始化提示中的“直接负责写稿”等文字不覆盖已采用的新职责。项目总控和部门总控不展开长篇正文或承担具体制作，简短咨询可就地解释。讨论话题可以充分讨论自己的主题，但不能把未选择的分支当成正式制作要求；执行话题只做收到的授权任务。用户在总控提出写作要求时，总控读取已有资料、补必要缺项并交给执行话题，随后汇总实际结果。

宿主侧栏里的聊天仍可平级显示；父子关系来自本项目的会话登记，不宣称客户端具有原生嵌套聊天。后台临时子 Agent 是当前执行轮次的协作工具，不是用户可长期接续的项目聊天，不能用它代替 `create_thread` 和真实绑定。

## 身份、复用与数据

- 一个会话节点归属一个明确项目和职责范围。不得把所有作品的灵感汇集到一个通用灵感库，不用相似标题认领其他项目的聊天。
- 同一灵感的后续讨论复用同一话题；同一任务的继续、返修与恢复优先原执行话题。新灵感、新交付范围或互相独立的任务使用独立话题。不能以新标题、新聊天或新任务绕过旧任务锁、范围占用、未知发送或未决成果。
- 会话登记保存逻辑层级、精确来源和宿主观察；原话及分支保存到本项目 `planning.record`，正式正文沿用成果与任务机制。它们使用同一作品登记体系，职责不同，不再建立第二份权威灵感库。
- 任务交接固定选中来源的准确版本和实际取得的正文。develop 选择的 planning_record 版本与 branch 是冻结创意来源，保留在任务 inputs 供阅读，并在成果来源元数据保留准确引用、分支和摘要；后续讨论新版不会自动使它失效或替换它。其余剧本、风格等业务依赖仍按原时效校验，不能把冻结创意来源当成忽略所有旧依赖的许可。最新候选、当前通过版、用户选中讨论版本和任务冻结输入分别读取，不按文件修改时间或“最近聊天”推断。
- 原始记录、删除前记录、准确成果与执行锁继续保留。聊天窗口不作为唯一存储；上下文过长时保存完整检查点和有来源的交接，再按明确范围接续，不能只留一句总结代替正文。

## 灵感进入、决定和交编剧

1. 灵感总控收到属于本项目的新想法，先保存可取得的用户原话、来源、附件引用和未知项，再准备该想法的独立讨论话题。只有用户要求“仅登记”时不自动启动讨论。已有相同灵感核对稳定身份后复用，不因措辞变化重复创建。
2. 讨论话题按包内灵感方法持续探索，未选方向时保持多分支发散，明确选择后才系统深入；连续保存原话、分支、探索阶段和决定；以当前真实授权执行讨论，不自行写正式剧本、批准 Canon 或创建另一个同类灵感总控。
3. 讨论后的选择为保留、删除，或将准确选中版本交编剧处理为剧本/小说。保留可以是完整结果，不自动转制作。“可以考虑”只记录为倾向；用户已经作出明确选择且授权后续工作时直接继续，不再索取固定确认词。
4. 删除采用可恢复的项目内回收记录，并依据实际用户删除范围处理宿主聊天归档。用户已授权该话题回收并归档时直接准备两者，不再问一次归档确认；仅要求本地回收则只处理本地。回收与宿主归档分别核验，保留原话、版本及已有引用，不物理删除作品正文或已产生成果。宿主归档失败、未知或无能力时保留待办，不能把本地回收写成聊天已归档。恢复已回收话题时沿用原身份；需要重新显示宿主聊天时，核实原真实 ID 并按恢复请求取消归档。
5. 转剧本/小说时冻结选中讨论记录与分支的准确版本，交编剧总控；后续讨论产生新版也不静默改变已交接输入。选择不自动改动整个项目路线或历史分类；本版执行仍检查既有路线，目标形式不兼容时保留精确交接，由编剧只澄清或拒绝，不能标 ready 或悄改路线。
6. 编剧总控先读已有项目要求、准确选中来源、现有大纲/正文与相关设定，只澄清会改变本次写作的缺项。明确要大纲、正文、某集、某场或修订后，复用或建立独立执行话题；用户已明确正文时不强加大纲或小说底稿前置。

直接交给编剧的明确需求无需先造灵感话题或伪造交接记录。编剧总控读取既有准确输入与用户要求，补缺项后按直接需求路径准备执行话题；准确输入、交付范围、允许改动和任务锁同样保留。

## 宿主执行链

登记工具记录计划和观察，不调用宿主创建、发消息、等待或归档。承担本轮协调的工作对话应完成下列已授权动作；只写“待办”而跳过本轮可执行动作不能算完成。专业话题不得递归调用 `workspace.prepare` 建整套工作区，也不得再为自己创建一个同职责总控。

1. **读状态与授权。** 使用显式 root 的 `film_conversations` 读取层级、话题、派发及待办，核对当前会话身份和所属部门。读取本轮用户要求或可核验持续授权的原话、范围和来源，区分允许创建、发送任务、回报与归档的实际范围。宿主发消息的授权须来自人类；被派发方的“请回复”本身不是授权，但随任务传递的有效人类授权证据可以核查使用。通用包不为其他用户生成持续授权。
2. **准备与领取。** 先保存准确父节点、职责、话题/任务范围、来源引用和稳定操作号。将外部动作登记为待办，只领取本轮可执行的具体动作。重复领取回执、超时、排队与未知都不是再次执行外部动作的许可。恢复时先读已有观察和原请求，不改变操作号或目标。
3. **创建或复用真实聊天。** 创建前 `list_projects` 核实正确客户端项目与授权作品目录；复用则 `read_thread` 核对真实 ID、实际项目、职责和范围，保留用户现有标题与历史。需要创建且授权覆盖时，用 `create_thread` 一次提交明确初始提示和准确 project target。不能用别的作品、通用聊天或 projectless 冒充已归入本项目。本版初始提示只要求核对本职责、报告就绪并等待派发，避免父对话尚未保存真实 ID 时子话题抢先建任务或开始创作。
4. **核对创建结果并绑定。** `clientThreadId` 仅是排队引用，不能传给要求 threadId 的工具。取得真实 threadId 后保存真实观察并用 `film_projects bind` 关联本作品；作品绑定、层级绑定与客户端侧栏归属分别核实。必要的归属操作使用 `move_thread_to_project`，不得移动无关聊天或改全局排序。创建成功但登记未完成只补登记，不重建聊天。
5. **创建任务并派发。** 保存真实创建观察并完成 `film_projects bind` 后，所属部门总控按实际模块返回的 task_module 使用 `film_task_create` 创建唯一任务，传该话题真实 thread_id，冻结准确输入、范围、交付要求与执行锁，再 `bind_task`。随后 `start` 保存发送待办，领取后实际 `send_message_to_thread`；灵感话题没有正文任务，绑定完成后直接 `start` 讨论。执行方接收准确 task_id 后读取既有任务，不创建副本。actor 必须是当前实际工作聊天；项目总控不能填目标部门 ID 冒充其已接收或绑定。`observe`、`bind_task` 和“已就绪”均不自动派发。
6. **有限等待与观察。** 对真实 threadId 用 `wait_threads` 有界等待并保存游标；当前轮次先等待一次，再据状态继续有意义的等待或处理独立工作，避免高频重复读取。单次等待宜不超过 60 秒，保留沟通机会。只有需要正文、来源或核对未知结果时读 `read_thread`。返回需要用户决定、执行阻塞或当前轮次不能继续时，保存实际观察和下一动作，不把超时当失败或完成。
7. **核验成果与回报。** 执行方保存完整正文/方案、检查点和准确成果引用，核验任务实际提交及本轮完成范围后调用 `complete`；完成登记不依赖外发权限。已有授权覆盖回报时可准备向所属部门总控和项目总控的准确待办；缺少权限则保存完成事实与待回报原因，后续用 `report` 接续同一准确成果。宿主真实 `send_message_to_thread` 并观察受理后才报告发送情况，不把待办写成已回报；两级总控必须读取实际完整成果和任务状态后汇总。任务已提交但未登记完成时，先核验准确任务及输出，再补完成登记，不改旧 topic.status 掩盖差异。任务完成、讨论关闭、候选保存、质量审查、云稿同步和用户采用分别判定，回报失败不丢失已保存成果。
8. **核对归档。** 对已确认删除/关闭且授权归档的准确话题，宿主调用 `set_thread_archived(archived=true,threadId=真实ID)`，再按真实返回及必要查询保存观察。未知先查询原聊天的归档状态；恢复请求使用同一真实 ID 取消归档。归档不意味着物理删除，不能以本地删除状态证明宿主已归档。

宿主调用创建或发消息结果未知时，优先查询原操作和真实会话。只用实际返回的 operationId 调用对应状态工具；没有专用查询时结合 `list_threads`、`read_thread` 和必要的归档列表，按初始提示里的项目、父节点、请求标识、范围及准确来源核对。标题相似或等待很久均不足以认领、判失败或重发。无法确定时保留原未知请求，不换号、不建替代话题、不重新派发。

## 初始提示与接续包

初始提示应是可读的任务说明，并携带从真实登记取得的标识，不能为凑齐模板编造 ID。最小内容为：

- 授权作品目录和项目 ID、当前分层模式、当前节点职责、准确父节点及已知真实上级聊天；保留实际标题，不用推测标题替代身份。
- 当前节点是部门总控、专题讨论还是执行话题；本轮只做的任务、允许修改的范围、不属于本轮的工作、原用户要求与适用持续授权来源。
- 稳定创建/派发请求标识、准确来源记录及版本、已有 task_id 或由谁创建任务、当前执行锁和需要复用的云稿引用。
- 完整成果保存位置、完成判据、真实回报目标与人类授权证据；如果回报未获授权，仍按真实成果登记完成，另保留未完成的回报状态，不自行发送或声称回报成功。
- 明确“只核对本职责，不调用 workspace.prepare 创建整套项目，不另建相同总控或重复任务；执行前先读取当前登记与已有任务，未知先核查”。

新建话题的初始提示只确认就绪并等待，实际业务通过后续 `start` 待办发送。派发提示包含已绑定的真实任务及冻结输入，收到后直接做已授权工作，不再询问是否开始；不能把创建提示当成业务已派发。已有话题的显式新轮使用 `continue`，沿用同 topic_id 和真实聊天，保留旧任务及输出；仅在原轮安全完结后建立新任务，不换话题规避未决状态。接新跨部门转交时在 continue 提供准确 ready 的 route_id，原部门、范围、目标成果及输入须吻合；未带 route_id 是直接接续，本轮不继承旧转交的外发目标。旧轮来源和未完成回报保留在 task_history，可按原轮成果补 report。

## 持久恢复和能力边界

当前宿主工作轮次负责领取、创建、发送、等待、查询和记录观察。未完成动作持久保存后，后续进入本项目的授权协调轮次从原请求接续。没有后台常驻调度器；不保证用户离线或关闭客户端后自动唤醒，也不将持久待办、领取成功、发送成功、子聊天结束或本地观察等同于业务完成。

宿主能力不可用、真实 ID 未知、项目归属未核对、缺少必要人类授权或有未决旧任务时，保存具体缺项和已完成部分。缺项只阻止依赖它的动作，不影响其他已授权独立工作。旧任务按原冻结方法接续；采用分层模式只改变管理关系，不重写旧 execution_lock 或复制旧任务绕过限制。
