# 项目工作对话

适用于使用者明确要求搭建工作区、创建工作对话，或已核实其个人默认包含这些操作。新建作品及本地目录入口先读[项目搭建](project-bootstrap.md)；没有创建聊天授权的新使用者首次只确认一次整套主要入口，不能把包内流程或开发者授权当成使用者授权。看板只打开已关联对话，不发起工作；普通提问和仅浏览不初始化聊天。具体请求字段由 `film_workspace` 的参数定义与系统 `../../../docs/integration-workspace-1.11.0.md` 提供。

## 路线与职责

先读取实际项目和用户已选路线；未选路线不自行推断。novel_only 默认建立总控、灵感需求、小说人物、质量复核四类；screenplay 使用总控、灵感需求、美术总监、剧本分集、导演特效、资产提示词、质量复核七类；novel_to_screen 加上小说人物共八类。纯小说只有用户明确需要美术入口并授权初始化时，在 workspace.prepare 使用 include_art=true 增加 art 职责，共五类，不强制转影视。分集、人物、场景专属对话按后续明确工作建立，研究按主题建立。角色是工作入口，不自动启动对应创作。

老项目暂缺 art 槽位时，解析返回的 legacy_control_fallback 仅表示保留真实总控入口，不代表已建好美术对话。按本次授权补建缺项后再使用新入口；现有任务的真实 thread_id 与冻结方法优先，不因新增角色挪移任务、改旧执行锁或重建云稿。影视研究仍按主题独立，不把旧研究聊天因标题类似自动认领为美术职责。

小说人物和剧本分集职责均调用统一编剧的适用模式，既有角色槽位、scope 和对话关联保持；不为技能合并自动重命名、合并或删除聊天。直接剧本工作入口可从完整分场初稿开始，底稿可选。导演反馈通过准确成果的意见记录交接，保存记录不等于已经给另一聊天发送任务。旧任务仍在原冻结运行环境接续；美术 art 入口与基准接续不受编剧方法合并影响。

## 初始化和恢复

1. 先用 `film_workspace(read)` 读取职责槽位与已有观察；明确要求初始化时 `prepare`，使用准确项目身份、当前 revision 和同一次操作号。重复初始化复用已完成槽位，只处理缺项。路线改变保留旧入口历史，不删除聊天或自动迁移旧任务。
2. 核对作品登记、全局项目绑定和宿主真实聊天。只按明确 threadId、职责和范围复用；相似标题不是关联证据。登记已存在但未经宿主核对时保持待核对，不直接当作健康入口。
3. 先调用宿主 `list_projects`，核对实际客户端项目 ID 和其工作目录与授权 root 一致；不能只凭同名或旧绑定。随后为确实待建槽位记录稳定请求，再执行一次 `create_thread`。初始化授权须来自本使用者的当前请求或已核实个人默认。没有可用客户端项目或宿主创建能力时保留“客户端项目待关联”，槽位保持未请求，不以 projectless 或另一个项目替代，也不因本地目录成功声称已建好客户端项目。
4. 总控为唯一工作区协调者。初始提示携带项目 ID、授权作品目录、职责/范围、initialization_id、slot_id、request_id、已知总控 ID 和准确可用来源引用，要求只核对关联、报告就绪并等待创作指令，明确禁止专业对话递归搭建整套工作区。不得因建立工作区而开始写小说、研究、生成素材、批准或给其他聊天发送消息。新聊天需读取的上下文应与职责相关，不复制整套无关历史。用户此轮同时明确要求创作时，另按实际授权执行相应任务。
5. 工具返回准备中的 clientThreadId 时只记录排队引用；取得真实 threadId 后才能记入作品对话与 `film_projects bind`。两种关联完成与 Codex 侧栏所属项目是不同事实，分别记录。记录为 host_reported 的状态是当时宿主观察，不能声称持续实时健康。
6. 创建、登记或绑定只有部分成功时，保留真实 ID 并补齐缺项，不能重新创建。结果未知先核查宿主任务或已建立的聊天，未确认失败前不重发 create_thread。操作号和初始化请求标识保持不变；不能因换聊天或重开面板重置未知状态。新建前先重新 read，只有待建且本轮首次成功领取的槽位才执行创建；同 op_id 的 request_started 缓存回执不是再次调用外部创建的许可。已请求、排队或未知的槽位只核查原请求。

把现有聊天统一归入对应客户端项目，需要本使用者的当前请求或已核实个人默认涵盖整理范围，且映射已核实；使用 `move_thread_to_project` 执行后再次核对真实归属。只复用确属该作品的聊天，通用讨论、开发与其他作品聊天不自动改绑。不改变全局侧栏排序来迁就局部归档。用户自定义标题保留，不能把本地登记改名冒充宿主聊天已改名。解除关联不删除真实聊天。

本地目录、目录库绑定、侧栏归属与就绪分别记录；`associated_observed` 只表示已保存观察，可能仍为 `host_reported_projectless`，不能据此报告全部归入项目。完成或部分完成后运行包内目录助手刷新项目导航与对话索引，保留准确观察时间及待处理原因。

排队恢复时先检查原工具回执：只有实际返回相应 operationId 才可调用该操作的状态工具，不把 clientThreadId 填入需要真实 threadId 的 read_thread/wait_threads，也不把它当作工作树 operationId。没有确定查询接口时，用 list_threads 找候选，再用 read_thread 核对初始提示中的准确项目、职责、scope 和原 request_id；初始化提示必须包含这些可核对标识。标题相似不足以认领。暂时取不到准确证据就保留排队，继续其他独立缺项，不用超时推定失败或重建。

## 打开、执行与接续

总控可以直接承接故事与大纲讨论、初版整理和已明确的修改，不强制用户为了同一轮讨论跳转。需要进入专业工作对话时按准确职责和范围接续，并读取同一成果的 `film_cloud` 关联；对话不是云稿身份，不能因更换聊天复制文档。完整初稿与每轮明确修订按[按轮云稿工作方式](cloud-round-workflow.md)继续保存和同步；初始化工作对话本身不触发建页或上传既有作品。

以本轮内容 category/stage 和准确范围解析对应槽位，优先复用专属范围，缺少时使用对应项目级职责入口。`navigate_to_codex_page` 只打开真实 threadId，不能据此声称已发送任务或已开始写作。打开失败保留旧 ID，核查是否归档、无权或已失效；不要直接造一个新聊天。

用户在工作对话明确授权向指定对话发送任务时，才能用 `send_message_to_thread` 发送准确要求。传递项目、职责、成果 ID/版本、用户原话、允许改动与已知缺项；随后导航。未知发送结果不自动重发。只点击“进入工作对话”不发送消息。

看板可查询已有记录并打开关联聊天；打开操作不触发继续创作。继续写作仍检查原任务执行锁；新对话、路线或系统版本不能解除原范围占用或改写旧锁。任务状态、聊天状态、作品版本及用户采用分别核对。
